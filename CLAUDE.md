# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Cadence AI — an event management system (protocol events, VIP hierarchy/kekananan ranking, seating, running order) for Johor state government events, with an AI chat assistant that can read and modify event data. Backend is Node/Express + PostgreSQL; frontend is Vue 3 + Vite, run as two separate processes/ports.

The repo is mid-refactor on the `dev` branch: a large set of previously-added modules (`src/dashboard`, `src/protocol-hierarchy`, `src/realtime-operations`, `src/running-order`, their controllers/routes/tests) has been deleted in favor of a smaller, flatter `events` / `vips` / `ai` surface backed by a single JSONB column. Don't resurrect the deleted modules or their patterns (factories/adapters/observers) — the current architecture intentionally moved away from that.

The repo root holds only two projects, each self-contained with its own `package.json`/`node_modules`/`.env`: `backend/` and `frontend/`. There is no root-level `package.json` — always `cd` into one of the two before running npm commands.

## Commands

Backend (from `backend/`):
```bash
cd backend
npm install
node src/server.js          # starts Express on $PORT (default 3000)
node tests/structured-command.test.js   # runs the one test file directly (no test runner/framework — plain node:assert script, throws on failure, logs "... test passed" on success)
```

Frontend (from `frontend/`):
```bash
cd frontend
npm install
npm run dev        # Vite dev server
npm run build
npm run preview
```

Database: run the SQL files in `backend/database/` **in numeric order** against Postgres (`01_schema.sql` is a destructive reset — drops and recreates all tables; `04_events_data_and_chat.sql` and later are additive migrations, safe to run against an existing DB).

Env vars (`backend/.env` for the backend, `frontend/.env` for Vite):
- Backend: `PORT`, `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `GEMINI_API_KEY`, `GEMINI_MODEL`, `GEMINI_SERVICE_URL`
- Frontend: `VITE_API_BASE_URL` (backend base URL, e.g. `http://localhost:3000` — required since frontend and backend run on different Vite/Express ports), `VITE_ANTHROPIC_API_KEY`

There is no lint/test/build script wired up in `backend/package.json` — it only declares dependencies.

## Architecture

**Layering (backend):** `backend/src/routes/*.js` → `backend/src/controllers/*.js` → `backend/src/repositories/*.js` → `backend/src/database/db.js` (a shared `pg` `Pool`). Routes are thin (bind controller methods); controllers hold request/response logic; repositories hold all SQL. Follow this when adding endpoints rather than putting queries in controllers.

**Event data model — single JSONB blob, not normalized tables.** Each row in `events` has flat SQL columns (name, type, date, venue, status) plus one `event_data JSONB` column holding the live working document: `running_order`, `vips`, `sources`, `seating`, `ai_context`. (A `traffic` section existed but was removed along with the traffic/motorcade and emergency-override UI features — don't reintroduce it.) `EventRepository.updateEventData()` does a shallow Postgres `||` merge of `event_data`, keyed by top-level section. `EVENT_SELECT` in `EventRepository.js` is the single place that shapes the API's event JSON (aliases `event_id → id`, pulls each `event_data` key out with `COALESCE` defaults) — update it there, not per-query, when the event shape changes. Note `event_extractions` (a separate JSONB-snapshot audit table keyed by `extraction_type`) is a distinct, append-only history of published section snapshots, not the live event state.

**AI chat → tool-calling flow.** `POST /api/ai/chat` (`AIController.chat`) calls the Gemini API directly (no SDK, raw `fetch`) using native function-calling (`tools: [{ functionDeclarations }]` in the request body, `functionCall` parts in the response) rather than asking the model to emit a hand-described JSON envelope — argument shape is enforced by Gemini itself per-tool, not by prompt text. Every AI-reachable capability is a separate tool: one file per feature domain under `backend/src/ai-engine/tools/` (`runningOrderTools.js`, `vipEventTools.js`, `seatingTools.js`, `sourceTools.js` for the four `event_data` JSONB sections; `eventMetadataTools.js` for the flat `events` columns; `vipDirectoryTools.js`/`vipRankingTools.js` for the master `vip_profiles`/`vip_rankings` tables; `rsvpTools.js` for `event_vips`), each exporting `{ declarations, handlers }` and aggregated by `backend/src/ai-engine/tools/index.js` (`allDeclarations`, `dispatch(name, args, context)`). `AIController.chat` sends one Gemini request per turn, dispatches at most one tool call, and synthesizes the user-facing reply itself from the handler's result — no second model round-trip. The four JSONB-section tool files share `getCollection`/`setCollection`/`backfillIds`/`appendItem`/`updateItem`/`deleteItem`/`replaceSection` helpers from `backend/src/ai-engine/tools/collectionHelpers.js`, which abstract over plain-array sections (`running_order`, `vips`, `sources`) vs. the nested-collection section (`seating` → `seating.layouts`) and always assign new item ids via `crypto.randomUUID()`, never trusting one from the model; `update`/`delete` tools target a single existing item by its `id`, which the model must copy verbatim from the event data it was given. `backend/src/ai-engine/tools/sectionPersistence.js` writes the changed section back via `EventRepository.updateEventData` and, for `running_order`/`vips`/`seating` (mapped to `event_extractions.extraction_type` values `running_order`/`vip_list`/`seating_layout`), also writes an `event_extractions` snapshot — `sources` is intentionally not snapshotted there, since `event_extractions` is for interpreted/extracted data, not raw uploaded documents. Source-document text sent to the model is trimmed per-turn by `backend/src/ai-engine/services/sourceContextBuilder.js` (keyword-overlap relevance scoring, not full-text-every-turn) rather than the frontend dumping every source's full content on every request; a real embeddings/vector-retrieval RAG layer is a deferred follow-up, not yet built (see AI Model Engineering below). RSVP invites are the one AI action with a mandatory human-in-the-loop step: `rsvpTools.js`'s `stage_rsvp_invite` never calls `EmailService` itself — it only resolves the VIP and returns a `proposedAction` in the chat response, which `AiChatTab.vue` renders as a confirm/cancel button; confirming calls the existing `POST /api/events/:eventId/invite` (`RsvpController.invite`) directly, the same path a human uses from `RsvpTab.vue`. `update_rsvp_status`/`uninvite_guest` (staff overrides, no external side effect) and `set_vip_ranking`/`create_vip_profile`/`update_vip_profile`/`update_event_metadata` execute directly like the JSONB-section tools, no confirmation step.

**Document parsing.** `WorkspaceView.vue`'s `handleUpload` extracts real text from uploaded sources client-side — `pdfjs-dist` for PDF, `mammoth` (`extractRawText`) for DOCX, plain `file.text()` for txt/md/csv/json — capped at 20000 chars, stored on `source.content`. A source only becomes `status: "parsed"` if extraction actually produced content. `AiChatTab.vue` includes all sources' content (plus `running_order`, `vips`, `seating`) in every chat request's context, so the AI can read uploaded protocol documents directly; the "Generate from Documents" button in `RunningOrderTab.vue` just fires a canned prompt through `AiChatTab`'s exposed `sendMessage` telling the AI to build the running order from that context via a `replace` command.

**Frontend.** Single-page Vue 3 app (no router in use despite `vue-router` being a dependency) — `App.vue` holds top-level state (`currentUser`, `events`, `currentEvent`) and switches between `AuthScreen` → `EventsView` → `WorkspaceView` by conditional rendering. `WorkspaceView` hosts the per-event tabs (`RunningOrderTab`, `VipListTab`, `SeatingTab`, `RsvpTab`, `AiChatTab`, `SourcesPanel`), each corresponding to one `event_data` section (except `RsvpTab`, which talks to the relational RSVP endpoints below, not `event_data`). Running Order is not a top-level workspace tab — it's reachable only via the `ModulesPanel` side list, alongside the four main tabs (VIP List, Layouts, RSVP, AI Assistant). `services/api.js` is a thin fetch wrapper requiring `VITE_API_BASE_URL` since the frontend and backend are separate Vite/Express processes.

**RSVP & invitations — relational, not JSONB.** Unlike the rest of the event document, guest invitations live in real Postgres rows: `vip_profiles` (master directory of people — VIPs *and* general participants, distinguished only by `vip_category`, which includes a plain `'guest'` value for non-VIP invitees) joined to a specific event via `event_vips` (the RSVP status per event: `attendance_status` IN `invited|confirmed|declined|absent|arrived|attended`, plus an `rsvp_token` used for passwordless accept/decline). `RsvpController`/`EventParticipantRepository` (`backend/src/controllers/RsvpController.js`, `backend/src/repositories/EventParticipantRepository.js`) handle: `GET /api/vips/search?q=` (search the shared people directory), `POST /api/events/:eventId/invite` (creates/updates an `event_vips` row with a fresh token, sends the invite email, returns the created participant), `PATCH /api/events/:eventId/participants/:eventVipId` (staff-side edit of role/plus-one/arrival/notes/rank override), `PATCH /api/events/:eventId/participants/:eventVipId/status` (staff-side manual `attendance_status` override, distinct from the guest's own token-based response), `DELETE /api/events/:eventId/participants/:eventVipId` (uninvite), and the public, unauthenticated `GET /api/rsvp/:token/:decision` that the recipient clicks from the email — it updates `attendance_status` and renders a plain HTML confirmation page (not JSON; a human loads this directly in a browser). **Email is sent from the backend** via `backend/src/services/EmailService.js` (`nodemailer` over SMTP — `SMTP_HOST/PORT/USER/PASSWORD/FROM` env vars), invoked directly from `RsvpController.invite`; there is no `mailto:`-link flow. If a `vip_profiles` row has no email on file (true for most of the seeded kekananan data), the invite flow prompts for one inline and persists it via `VIPProfileRepository.updateVIP` (`updateEmail` still exists as a thin single-field wrapper around it, kept for callers that only need to set the email). AI-triggered invites go through an extra staging step — see the AI chat flow above.

**Backend conventions (ported from the Greenstep project's design, see `Knowledge/architecture-decisions.md`):**
- **Protected by default.** Every router except `authRoutes` (`/register`, `/login`) and `rsvpRoutes` (`GET /:token/:decision`, the public token-based responder a recipient opens from an email with no session) applies `authMiddleware` via `router.use(authMiddleware)` at the top of the file. When adding a new route file, mount it under `/api/events`, `/api/vips`, or `/api/ai` in `server.js` (already protected) or explicitly decide it needs to be public and say so in a comment — don't leave protection implicit.
- **Centralized error handling.** `backend/src/middleware/asyncHandler.js` wraps async controller methods at the route-registration call site (`router.get("/", asyncHandler(controller.getAllEvents))`); controllers no longer catch-and-500 unexpected errors themselves — they only handle *expected* branches (400/404/409/502 with a specific message) via early `return res.status(...).json(...)`. Anything else propagates to `backend/src/middleware/errorHandler.js`, mounted last in `server.js`, which logs server-side and returns a generic `{ error: "Internal server error" }` rather than leaking a raw DB/driver message to the client. `RsvpController.respond` is the one exception — it renders an HTML confirmation page (success and error), so it keeps its own manual try/catch instead of going through the JSON error handler.
- No live seed/reset endpoint was added — Postgres seed data stays as plain SQL files in `backend/database/` (see `02_seed_kekananan.sql`, `05_seed_demo_events.sql`, `08_seed_test_participant.sql`), run manually like the schema migrations.


## AI Model Engineering
- The AI has full CRUD across every feature via the tool-calling architecture described above: running order, per-event VIP list, seating layouts, sources, event metadata (name/date/venue/status/times), the master VIP directory, VIP kekananan ranking, and RSVP/invitations (invite is staged for human confirmation; status/uninvite are direct). Document → running order generation ("Generate from Documents" in `RunningOrderTab.vue`) works via `replace_running_order`.
- **Not yet built — deferred RAG phase:** a self-updating knowledge graph/vector store that automatically ingests uploaded documents and AI actions into persistent, queryable nodes (e.g. Postgres `pgvector` + entity-extraction on upload), replacing today's keyword-overlap trimming (`sourceContextBuilder.js`) with real semantic retrieval, and enabling cross-event/cross-document knowledge instead of per-event-only context. Scope this as a separate follow-up before starting it.
